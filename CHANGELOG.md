# node-coradb change log

## Version 1.0.0 (Nov 2, 2026)

The driver now behaves like the CoraDB JDBC driver wherever the two differed on the wire or in their transaction rules, reads several results from one request, and has the bugs of the 0.9.9 review fixed. Several behaviours change on purpose (see "Change" below). [COMPARISON WITH CUBRID DRIVER.md](COMPARISON%20WITH%20CUBRID%20DRIVER.md) sums up how the driver now differs from node-cubrid.

- Change: the package is published under the CoraDB npm organization as `@coradb/node-coradb` (`npm install @coradb/node-coradb`, `require('@coradb/node-coradb')`); `publishConfig.access` is `public`.
- New: `executeMulti(sql, params, options)` runs several statements (`;`-separated) in one request and reads them result by result, as a JDBC Statement does after `execute()`: a `MultiResult` with `isResultSet`, `getResultSet()`, `getUpdateCount()`, `getMoreResults()` (NEXT_RESULT), `close()`, and async iteration. It sends `CCI_EXEC_QUERY_ALL`; values are bound across the statements. `src/packets/NextResultPacket.js`.
- New: `index.js` exports `Cursor`, `PreparedStatement` and `MultiResult` (declared in `index.d.ts`, they were undefined at run time).
- New: `query(..., { getGeneratedKeys: true })` resolves with `generatedKeys`; `casId`; `CASConstants.CAS_PROTO_INDICATOR`, `CAS_RENEWED_ERROR_CODE`, `CAS_SUPPORT_HOLDABLE_RESULT`, `CAS_RECONNECT_WHEN_SERVER_DOWN`, `CAS_INFO_*`, `CCIPrepareOption.CCI_PREPARE_XASL_CACHE_PINNED`; `GetSchemaPacket.patternFlag()`.
- Change: `setAutoCommitMode()` (and so `beginTransaction()` / `endTransaction()`) commits the pending work when the mode changes, as JDBC's `setAutoCommit()` does; if the commit fails, the mode is unchanged. It used to change only the flag.
- Change: results are asked for as holdable (`CCI_PREPARE_HOLDABLE`, `CCI_EXEC_HOLDABLE`) when the broker supports it, as JDBC does by default: a cursor or a `query()` handle survives a commit. `rollback()` closes the open results (not prepared statements); `closeQuery()` of one of them afterwards succeeds. Without holdable results, `commit()` closes them too.
- Change: COMMIT and ROLLBACK are sent only when the CAS reports a transaction open (the status byte of its CAS info), as JDBC sends them.
- Change: the CAS info of every reply is kept and sent back with the next request; it was the login's for ever.
- Change: the client-info exchange announces renewed error codes and holdable results (`0xC0`, as JDBC). CAS errors come in the new numbering (`-10007`, was `-1007`); old-numbered ones from a broker that does not renew them are converted, as JDBC converts them. A negative broker port answer is now that CAS error, not `NEW_BROKER_PORT`.
- Change: the login reply is read as JDBC reads it: the CAS id (`casId`; `sessionId` keeps the same number) and the 20-byte session id, which the next login sends back so that a reconnect asks for the same session (the CoraDB server answers a reconnect after an abrupt disconnect with a new one). `close()` forgets it. A new session id at the end of an error reply (brokers that reconnect to their server) replaces it.
- Change: a statement that fails because the connection was lost, or with -111, -199, -224 or -677, is run once more on a new connection when it was the first statement of its transaction (`query()`, `executeWithTypedParams()`, `sql()`, `cursor()`, `stream()`, `executeMulti()`, `prepare().run()`), as JDBC does. Not after `close()` or `abort()`.
- Change: on a broker with statement pooling, a prepared statement whose handle the broker dropped (`CAS_ER_STMT_POOLING`) is prepared again (with the plan pinned from protocol V7) and run; one whose session was lost is prepared again on the new session instead of failing with `STATEMENT_CLOSED` (which stays for brokers without pooling).
- Change: generated keys are read the way JDBC's `executeUpdate(sql, RETURN_GENERATED_KEYS)` reads them: the INSERT is sent without auto-commit, the keys are read at once, the handle closed and, in auto-commit mode, the work committed — all before `query()` resolves. `getGeneratedKeys(handle)` answers from the keys read; `closeQuery(handle)` forgets them. With auto-commit on, the CAS committed the INSERT at once and dropped the keys, so `getGeneratedKeys()` failed.
- Change: `requestTimeoutMs` also limits the original methods (`query()`, `execute()`, `commit()`, `fetch()`, `getSchema()`, the LOB methods...).
- Change: query handles carry the login they belong to: after a reconnect, `fetch()`, `closeQuery()`, `getMetaData()` and `getGeneratedKeys()` refuse an old handle (`NO_ACTIVE_QUERY`) instead of acting on the new session's statement with the same number. The first login's handles are unchanged.
- Change: `getSchema(CCI_SCH_CONSTRAINT, table)` matches the table name exactly; `CCI_SCH_ATTRIBUTE` treats it as a pattern only when it is missing or holds `%` or `_` (JDBC's flags). `_` was a wildcard in every table name.
- Change: after each `lobWrite()`, the LOB's new size is written into its packed handle (JDBC's `setLobSize()`).
- Change: SQL text is logged at debug, not info, and bound values and rows are no longer logged.
- Fix: `getSchema(CCI_SCH_CONSTRAINT)` read NUM_PAGES and NUM_KEYS as shorts; they are ints, so any table with an index broke the reply. Fields are read at their real sizes, and columns the driver does not know are skipped. Views are typed `'User view'` (was `'Unknown (1)'`).
- Fix: `getSchema()` fetched once and silently dropped the rows a reply did not carry; it fetches until it has them all. It refuses the schema types it cannot read (`INVALID_SCHEMA_TYPE`).
- Fix: a BLOB / CLOB parameter that was not the LOB object `lobNew()` / `lobWrite()` returned was sent anyway (and corrupted the packet); it is refused with `INVALID_PARAMETER`. The LOB locator is sent byte for byte (it was decoded and re-encoded as UTF-8).
- Fix: `execute([...], params, callback)` sent the `?` unbound and never called the callback; values are bound across the statements.
- Fix: `execute()` of several statements (EXECUTE_BATCH) did not send the query timeout.
- Fix: `queryAsObjects()` of a statement without rows threw a TypeError and leaked the handle; it resolves with `[]`.
- Fix: `getDatabaseParameter('MAX_STRING_LENGTH')` always failed; it reads the value (setting it is still refused).
- Fix: `logger: null`, or a logger without every level, broke every request.
- Fix: a cursor whose `next()` timed out while the fetch still completed lost that batch; the next `next()` returns it.
- Fix: `cancel({ timeout })` with an invalid timeout could crash the process; timeouts given as strings or negative numbers no longer break every connect; `createConnection(null)` no longer throws.
- Fix: requests failed together shared one error object, and the running one's statement showed on the others.
- Fix: the text formatter turned every surplus `?` after the first into NULL, wrote invalid Dates as `NaN/NaN/NaN`, Buffers as UTF-8 text and objects as `[object Object]`.
- Fix: `isUpdatable` was read inverted on the new-protocol path; column metadata had both `Scale` / `Precision` / `IsNullabe` (defaults) and the real `scale` / `precision` / `IsNullable` (the old names are now aliases).
- Fix: `transaction()` whose function throws something that is not an Error threw a TypeError.
- Fix: `index.d.ts`: `SchemaType` lists what `getSchema()` reads, `getMetaData()` may resolve `undefined`, a `Timezone` type is declared, and the `CASConstants` name functions work when taken off the object.
- Removed: dead code `PacketReader._parseSequence()` / `_parseResultSet()`, `PacketWriter._writeSequence()` / `_writeObject()` / `_writeResultSet()`, a duplicate `PacketWriter.addDateTime()`, and the parameter branches for OBJECT and RESULTSET (they declared one length and wrote another).
- Package: `files` limits the published package to `index.js`, `index.d.ts`, `src/`, `CHANGELOG.md` and `COMPARISON WITH CUBRID DRIVER.md`. The license field is the SPDX id `BSD-3-Clause` (it was `BSD`, which npm does not recognise); `repository`, `homepage` and `bugs` point to github.com/apsisware/node-coradb over https (git:// is deprecated); `"type": "commonjs"` is declared; `prepublishOnly` runs the lint and the unit tests before a publish.
- Fix: a time-zone value in the hour repeated when daylight saving time ends (01:30 on 2017-11-05 in America/New_York) names two instants, and the server says which with its abbreviation (EDT or EST). `Timezone` ignored it and always took the standard-time reading, so a value sent as EDT had `tzh` -05 and a `valueOf()` an hour late. The abbreviation now picks the reading when it names one (by its English name, or as an offset such as `-02`).
- Fix: a MULTISET parameter of strings was refused by the server (-454, "Invalid data type referenced"). Every collection parameter (`set`, `multiset`, `sequence`/`list`) now goes on the wire as a SEQUENCE, as the JDBC driver binds them (`UStatement.bindCollection()`); the server makes it the column's type. The declared type still decides the element type.
- Change: the per-file db-test runner (`run-db-tests.ps1`, `run-db-tests.bat`, `npm run test:db:each`) is removed: the suites clean up their own tables, and one file runs with `npx mocha --require test/db-test/testSetup/suiteHooks.js <file>`.
- Change: removed what the project no longer needs: `tools/check-cancel.js` (the live tests check the broker cancel), `BUILD.md` (its prerequisites and notes are in `RUN-TESTS.md`), the `clean` script, and `test/unit-test/test_SetAutoCommitMode.js` (a copy of `test_SetAutoCommitModePacket.js`).
- Test: `test/unit-test/test_CoraDBConnection.fixes.js` (the review fixes) and `test_CoraDBConnection.jdbc.js` (the JDBC behaviours on the wire); the pretend CAS reports the transaction status and the broker's flags, and hands out session ids. The db-tests run against the official `olympics1988-2004` dataset (as `dba`), and `test_CoraDBConnection.jdbcParity.js` checks the JDBC behaviours on the live server. New live suites for what was only tested against the pretend CAS: `test_CoraDBConnection.prepare.js` (`prepare()` / `run()` / `close()`, typed values, re-prepare after a lost connection, and `transaction()`: commit, rollback, a failing statement, `TRANSACTION_IN_PROGRESS`, `TRANSACTION_LOST`), `test_CoraDBConnection.stream.js` (`stream()`, `getQueryPlan()`) and `test_CoraDBConnection.cancel.js` (`cancel()` through the broker and by abort, `abort()`, `setQueryTimeout()`, `setRequestTimeout()`, `canBrokerCancel()`, `getCasProcessId()`, `getConnectedHost()`, `getQueueLength()`), and `test_CoraDBConnection.dataTypes.js`: every column type written as literals, bound by `sql()`, `prepare().run()` and `executeWithTypedParams()`, and formatted into the text by `execute(sql, params)`, then read back by `sql()` (bound, text, old protocol), `query()`, `queryAllAsObjects()`, a cursor across fetch batches and `queryAll()`; NULLs, edge values (unsafe BIGINT, exact NUMERIC, the zero date, NULL in a collection), and time-zone values (LTZ in the session's zone, the repeated DST hour, `format()`). Each suite drops the tables it creates before it starts and after it ends (`suiteHooks.js`, loaded by the npm scripts). The e2e connection is set in one place (`test/e2e-test/helpers.js`, overridable with `CORADB_*` environment variables); new scenario `test_MultipleResults.js`. Three db-test checks that could not fail (`return new Error(...)` where `throw` was meant) now do, and the CAS error codes are expected in the renewed numbering.
- Docs: `COMPARISON WITH CUBRID DRIVER.md`; README sections "executeMulti" and "As the JDBC driver does it".

## Version 0.9.9 (Oct 17, 2026)

One driver again. Two lines had grown apart since 0.9.3: the one kept in this repository (whose unreleased work added a connection check, generated keys, a server-side query timeout, charset-aware strings and collection parameters) and the one CoraDB WebSQL carried (0.9.4 to 0.9.8). This release is the WebSQL line with that unreleased work brought over and covered by tests. Coming from 0.9.3, read 0.9.4 to 0.9.8 below as well: several behaviours changed there on purpose.

- New: `isValid()` asks the CAS whether the session is still there (`CAS_FC_CHECK_CAS`). Resolves `true` or `false` and never rejects. A connection that is not open is `false` without a request: it does not connect. It queues like any other request.
- New: a server-side query timeout. `queryTimeout` (milliseconds; 0, the default, for none) as a connection option or the tenth positional argument of `createConnection()`, and `setQueryTimeout()` / `getQueryTimeout()`. It is sent with every statement — PREPARE_AND_EXECUTE and EXECUTE, so `query()`, `queryAll()`, `executeWithTypedParams()`, `sql()`, `stream()`, `cursor()` and `prepare().run()` alike. It is the server's limit, beside `requestTimeoutMs` / `timeoutMs`, which is how long the driver waits.
- New: generated keys. `query(sql, params, callback, { getGeneratedKeys: true })` (or `query(sql, params, { getGeneratedKeys: true })`) sets `CCI_EXEC_GET_GENERATED_KEYS`, and `getGeneratedKeys(queryHandle)` reads the keys the INSERT generated (`CAS_FC_GET_GENERATED_KEYS`) as a result set. The INSERT's handle has to be open, and is closed with `closeQuery()`; a handle that is not open fails with `NO_ACTIVE_QUERY` without a request.
- New: SET, MULTISET and SEQUENCE parameters. `{ type: 'set' | 'multiset' | 'sequence' | 'list', value: [...] }` in `sql()`, `stream()`, `cursor()` and `prepare().run()`, and the same names in `executeWithTypedParams()`'s `dataTypes`. The element type is given (`elementType: 'int'`, or in the name: `'set of int'`, `'list(varchar)'`) or worked out from the elements. Each element is checked and converted as a parameter of that type would be. 0.9.6 refused these types; the official line's unreleased version inferred the type from the first element only and sent the rest unchecked.
- New: strings are decoded in their column's charset, from the charset bits of the two-byte type: ISO-8859-1 and BINARY as Latin-1 (a BINARY value comes back whole with `Buffer.from(value, 'latin1')`), the rest as UTF-8. That includes a collection's string elements and the values of a CALL. The column's metadata has `Charset`, the Node.js encoding.
- New: `CASConstants.ColumnTypeMask`, `CollectionFlag`, `CharsetId`, `getCharsetEncoding()`, `confirmColumnType()`, and `CCIExecutionOption.CCI_EXEC_GET_GENERATED_KEYS`; `src/packets/CheckCasPacket.js`, `src/packets/GeneratedKeysPacket.js`.
- Fix: a column type sent in one byte (protocols before V7) was taken whole: its collection bits made a SET OF INT an unknown type. They are read as the JDBC driver reads them: the collection in bits 6-5, the type in bits 4-0.
- Change: an ASCII column's strings are decoded as UTF-8, not with Node.js's `ascii` decoder (which drops the high bit): the same for real ASCII, and UTF-8 text a server labels ASCII is not mangled. The official line's unreleased version used `ascii`.
- Change: `cancel()` is WebSQL's: it resolves with `{ method: 'broker' | 'abort' | 'none' }` rather than nothing, falls back to `abort()` when the broker cannot do it, and takes `{ brokerCancel, timeout, onlyWhile }`. `cancel(callback)` still works. The CAS process id is `getCasProcessId()` (the official line's unreleased version had a `casProcessId` property).
- Change: the constructor's ninth positional argument stays `requestTimeoutMs`, as it has been since 0.9.6; `queryTimeout` is the tenth (it was the ninth in the official line's unreleased version).
- Test: `test/unit-test/test_CoraDBConnection.v099.js` covers each of the above, the protocol parts against the pretend CAS over a real socket. The pretend CAS now sends column types in two bytes, as a V7+ CAS does, and can send a charset, a collection's element type, or the single byte of the older protocols. End-to-end scenarios from the official line: `test_Collections.js` (now also binding through `sql()`), `test_GeneratedKeys.js`, `test_IsValid.js`, `test_QueryTimeoutCancel.js`.

## Version 0.9.8 (Oct 11, 2026)

Fixes from the fifth code review: a version request (a ping) no longer commits an open manual-commit transaction, `queryAll()` no longer fetches for ever on a statement without rows, CALL and EVALUATE return their value, and `transaction()` runs one at a time. Several behaviours change on purpose (see "Change" below).

- Fix: `getEngineVersion()` always sent auto-commit = 1, and the CAS commits after answering one: a ping in the middle of a manual-commit transaction committed it, and a later rollback could not undo it. It sends the connection's real mode.
- Fix: `queryAll()` on a statement without rows (an UPDATE, a SAVEPOINT, a SET) took the count of changed rows for a row count and sent FETCH requests for ever — tens of thousands a second — and nothing else could run on the connection. Nothing is fetched for a statement without a result; the fetch loop also stops at an empty batch, whatever the row count said; and the count of rows read starts at 0 for every statement. `fetch(handle, true)` on such a handle resolves with no result and sends nothing.
- Fix: CALL, EVALUATE and GET STATISTICS were taken for statements without rows. `queryAll()` failed on them with a TypeError and left the handle open; `sql()` and `cursor()` lost the value. They are read as one-row results: the result is built from the column list, and the rows are fetched when the reply does not carry them. `query()` fetches that first batch itself rather than handing out an empty one with a row count of 1.
- Fix: a `connect()` made beside a request's own implicit connect (or two requests after a drop) failed the second with `CONNECTION_ALREADY_PENDING`, its statement unsent. A second connect now waits for the one in progress and shares its outcome.
- Fix: two `transaction()` calls at once shared the connection's one transaction: one's COMMIT committed the other's work, the first to finish turned auto-commit back on under the other, and the other's rollback was swallowed. A `transaction()` made while another is running fails with `TRANSACTION_IN_PROGRESS` and runs nothing. When `fn` fails and the rollback cannot be done on a session that is still open, it fails with `ROLLBACK_FAILED` (`cause`: what `fn` threw; `rollbackError`: why the rollback failed) and leaves auto-commit off — turning it back on would have committed the work with the next statement.
- Fix: `getSchema()` counted the table name pattern in UTF-16 units, not UTF-8 bytes: a pattern with a non-ASCII letter declared the wrong length and the server read the rest of the request out of step. An empty pattern, which goes as a NULL, is no longer counted as one byte.
- Fix: time-zone values (`Timezone`) took the month from the local zone among UTC fields, so 2026-01-31 23:30 Asia/Seoul printed as `2026-02-31` on a server east of UTC — in `toString()`, `format()` and everything built on them. `valueOf()` read the wall-clock time as UTC, off by the zone's offset; it is now the instant (through luxon). The offset (`tzh`, `tzm`, `getOffset()`) is the one in force at the wall-clock time, not hours away from it across a DST change. A zone written as an offset ('+09:00') is understood. `HH` / `HH12` write midnight as 12, not 00.
- Fix: typed DATE, DATETIME and TIMESTAMP parameters given as strings without a zone were parsed in the server's local time and sent in UTC, shifted by its offset. They are sent as written. A string with a zone, and a number, are still instants. A TIME parameter accepts '10:00:00' (and '10:00'), which was refused. A date that does not exist (a February 31st) is refused.
- Fix: two `fetch()` (or `Cursor.next()`) calls on one handle at once got their batches in reverse order, and a `closeQuery()` made after a `fetch()` ran before it. A handle's fetches and close keep their order among themselves (they still go ahead of other queued statements).
- Fix: the text formatter did not know `[bracket]` identifiers: an apostrophe inside one was taken for the start of a string, so the next value landed outside its quotes, in code position.
- Fix: an IPv6 host was split at its first colon ('::1' became host '' and port ':1'). '[addr]:port', '[addr]' and a bare address ('::1') are read as such. `maxConnectionRetryCount: 0` is honoured; it used to become 1.
- Fix: a zero date (0000-00-00) in a DATE, DATETIME, TIMESTAMP or time-zone column was decoded as `-000001-11-30`. It is null.
- Fix: an empty or blank string bound as a numeric type was sent as 0, and '0x10' as 16. Numeric parameters given as strings must be decimal numbers; anything else is refused with `INVALID_PARAMETER`.
- Fix: CLOSE_REQ_HANDLE always sent auto-commit = 0, which could keep a SELECT's transaction (and its locks) open after the handle was closed. It sends the connection's real mode, as the CCI and JDBC drivers do.
- Change: `queryAll()` (and `queryAllAsObjects()`) on a statement that returns no rows resolves with an empty result — no columns, no rows, `RowsCount` 0 (`[]` for `queryAllAsObjects()`) — rather than hanging.
- Change: `Timezone.prototype.valueOf()` returns the instant, not the wall-clock time read as UTC; `datetime` still holds the wall-clock time in its UTC fields. `format('HH12')` at midnight is '12'.
- Change: a zero date reads as null.
- Change: numeric parameters given as strings that are not decimal numbers are refused; zone-less date strings are wall-clock times.
- New error codes: `TRANSACTION_IN_PROGRESS`, `ROLLBACK_FAILED`. New error field: `rollbackError`.
- Test: `test/unit-test/test_CoraDBConnection.review5.js` covers each fix, the protocol ones against the pretend CAS over a real socket. Two existing assertions that described the old behaviour were updated in `test_Timezone.js`: `HH12` / `HH` at midnight is '12', and `valueOf()` is the instant.

## Version 0.9.7 (Oct 08, 2026)

Fixes from the fourth code review: connection loss now answers every waiting request, handles and transactions no longer survive the session they belong to, the value decoder no longer loses its place, and the text formatter no longer writes comments into statements. Two behaviours change on purpose (see "Change" below): a session lost while auto-commit is off is not silently replaced, and BIGINT / NUMERIC values that do not fit a JavaScript number come back as strings.

- Fix: a prepared statement, cursor or query handle from before a reconnect could act on a **different statement** in the new session, which hands out handle numbers from 1 again — `stmt.run()` after a drop ran whatever the new session had prepared under the same number. Each login now has a generation number; every handle, prepared statement and cursor is stamped with it, the handle table is cleared on every login and every socket close, and `run()`, `fetch()`, `Cursor.next()` / `close()`, the internal release and `close()` refuse or skip handles from an older login. A stale prepared statement fails with `STATEMENT_CLOSED`; a stale cursor or `fetch()` fails with `NO_ACTIVE_QUERY` and no longer reconnects to try.
- Fix: `transaction()` survived a lost session: the next statement reconnected silently, and `commit()` committed only the work after the drop. It now fails with `TRANSACTION_LOST`, sends nothing on a new session, and refuses to commit on any session other than the one it began in.
- Fix: `transaction()` turned auto-commit off at once, so statements queued *before* it joined it and were rolled back with it. `setAutoCommitMode()` (and so `beginTransaction()`, `endTransaction()` and `transaction()`) now takes effect in queue order and resolves once it has.
- Fix: a deadlock victim (-72) inside a transaction has had the whole transaction rolled back. The error is now `retryable: false` and `transactionRolledBack: true` when auto-commit is off (retrying the one statement would carry on as if the rest had happened), and `transaction()` fails with `TRANSACTION_ROLLED_BACK` (retryable: run the whole transaction again) instead of committing what came after — even when `fn` caught the error. With auto-commit on, -72 stays retryable.
- Fix: a clean close from the server (FIN — a CAS restart, a broker reset) never failed the request in flight, and the queue behind it hung for ever. Every way of losing the socket — error, FIN, timeout, an unreadable reply — now fails the request in flight (with the socket error, or `CONNECTION_CLOSED`) and every queued request (`CONNECTION_CLOSED`), and emits `disconnect`.
- Fix: a login on a reused socket (broker port 0) had no callback or timeout of its own; a reset during it left `connect()` pending for ever and every later `connect()` failing with `CONNECTION_ALREADY_PENDING`.
- Fix: after one failed `connect()` had used up every host and retry, every later `connect()` threw `TypeError … reading 'port'`, even once the server was back. Hosts and retries start over on each connect.
- Fix: `close()` while a request was still connecting left that request pending for ever. It is answered with `CONNECTION_CLOSED`, and the queue with `CLOSED_WHILE_QUEUED`.
- Fix: one `closeQuery` failing inside `close()` skipped `CON_CLOSE` and left the socket open. Each handle's failure is ignored, and the session is always closed. `close()` also now waits for the request already running instead of writing beside it.
- Fix: a parser exception (a reply the driver cannot read) escaped the socket's `data` handler as an uncaught exception and ended the process. It now fails the waiting request with `PROTOCOL_ERROR` and destroys the socket. The LOB read/write paths go through the same reader.
- Fix: a late `close` or `error` from the broker's socket, after it redirected the connection to a CAS port, could mark the new connection closed. The old socket's listeners are removed before it is closed.
- Fix: a timed-out request's cancel could hit the **next caller's** statement: "is my request still running?" was checked once, then the broker cancel took up to 2 s and the abort fallback fired regardless. It is now checked again immediately before the broker is asked and again before any abort; `cancel({ onlyWhile })` exposes the same guard and resolves `{ method: 'none' }` when it fails.
- Fix: `lobWrite()` at a non-zero offset used the LOB position to index the caller's buffer and sent empty chunks for ever. It keeps a separate position, and fails with `LOB_WRITE_FAILED` if the server accepts 0 bytes.
- Fix: SMALLINT was read unsigned (-1 came back as 65535), on every path.
- Fix: one shared value decoder for `query()`, `sql()` with parameters, `cursor()`, `prepare().run()` and `fetch()`, which always advances by the value's size. An unknown type used to come back as an Error object *as the cell value* and desynchronise every column and row after it; it now comes back as `{ type, typeCode, raw }`. The bound-parameter path now reads the time-zone types. SET / MULTISET / SEQUENCE values are decoded into arrays (they were skipped by a guessed size). GRAPH_OBJECT values come back as their text when the server sends text, otherwise as `{ type: 'GraphObject', raw }`.
- Fix: a two-byte column type (protocol V7+) for a collection kept only the element type, so a SET OF INT column was read as INT. The column is now a SET with `CollectionElementType` INT (`columns[i].elementType` in the everyday API).
- Fix: `include_column_info` on EXECUTE (a CALL, or a `?` in the select list) was ignored, and the description that followed it was read as the rest of the reply. It is parsed and replaces the statement's column list.
- Fix: `getSchema()` left a server handle open on every call; it is closed after the rows are read.
- Fix: login credentials went out as Latin-1, and a value of 32 bytes or more ran into the next field and corrupted the packet. They are written as UTF-8, and a database name, user or password of 32 bytes or more is refused with `INVALID_PARAMETER` before a socket is opened.
- Fix: the text formatter (`query(sql, params)`, `execute(sql, params)`, …) wrote `bal-?` with -5 as `bal--5`, commenting out the rest of the statement, WHERE clause included. Negative numbers and bigints are written in parentheses: `bal-(-5)`.
- Fix: the formatter wrote 7 ms as `.7` (700 ms); milliseconds are zero-padded to three digits.
- Fix: the formatter did not recognise `//` comments, so a `'` or `?` in one shifted every parameter after it.
- Fix: the formatter wrote MySQL-style backslash escapes (`\n`, `\\`, `\0`), which CoraDB stores literally under its default `no_backslash_escapes=yes`. Only the quote is escaped now, by doubling it. A string containing a NUL character, and a number that is not finite, are refused with `INVALID_PARAMETER`. On a server running `no_backslash_escapes=no`, bind on the server instead (`sql()`, `prepare()`, `executeWithTypedParams()`).
- Fix: small values read from a reply (CAS info, OIDs, LOB handles, BIT/VARBIT values) are copied out of it instead of being views that kept the whole reply in memory.
- Change: BIGINT values outside `Number.MIN_SAFE_INTEGER..MAX_SAFE_INTEGER` are returned as decimal strings, and NUMERIC values whose text would not survive `Number()` exactly are returned as strings. Everything else is still a number. (`index.d.ts`: see `CellValue`.)
- Change: when a session is lost while auto-commit is off, requests fail with `TRANSACTION_LOST` instead of reconnecting, until the caller calls `rollback()` (which then resolves without sending anything), `setAutoCommitMode()`, `connect()` or `close()`. `commit()` fails with `TRANSACTION_LOST` too. The same applies after `abort()` (and a `cancel()` that falls back to it) with auto-commit off.
- Change: `fetch()` and `closeQuery()` no longer reconnect a closed connection: a handle does not outlive its session. They fail with `NO_ACTIVE_QUERY`.
- New error codes: `CONNECTION_CLOSED`, `TRANSACTION_LOST`, `TRANSACTION_ROLLED_BACK`, `PROTOCOL_ERROR`, `LOB_WRITE_FAILED`. New error field: `transactionRolledBack`.
- Test: `test/unit-test/test_CoraDBConnection.review4.js` covers each fix, mostly against the pretend CAS over a real socket; `helpers/fakeCas.js` gained per-session handle numbers, raw values, scripted handlers, a cancel listener, a fixed port and a redirect target. Two existing assertions that described the old behaviour were updated: SMALLINT 0x8001 now reads as -32767 (`test_PacketWriter_PacketReader.js`), and `_escapeString` no longer writes `\b` as `\\b` (`test_Helpers.js`).

## Version 0.9.6 (Oct 08, 2026)

The everyday API, typed errors, server-side binding for reads, and callbacks that always settle. Everything is additive: existing names, arguments and result shapes keep working. See "The everyday API" in the README.

- New: `sql(sql, params, options)` runs one statement and resolves with `{ rows, columns, rowCount, affectedRows }` — rows as objects (or arrays with `rowsAs: 'arrays'`), every row read, the handle always closed.
- New: `stream()` (async iterable of rows; leaving the loop closes the handle), `cursor()` (batches under the caller's control; closes itself after the last row), `prepare()` (compile once, `run()` many times, `close()`), `transaction(fn)` (commit on resolve, roll back on throw, auto-commit restored).
- New: per-request `timeoutMs` and `AbortSignal` on all of the above, and a connection default (`requestTimeoutMs`, `setRequestTimeout()`). A stopped call fails with `TIMEOUT` or an `AbortError`; its waiting requests are removed from the queue, and its running request is cancelled — never another caller's.
- New: values for `?` are bound on the server with types worked out from the JavaScript value, or given as `{ type, value }`. Unknown types, values that cannot be bound and INTs that do not fit are refused with `INVALID_PARAMETER` before anything is sent. NULL is bound (it was not supported at all).
- New: `CoraDBError` (`code`, `casCode`, `statement`, `statementIndex`, `retryable`) for every failure the driver produces, `CoraDBBatchError` (an `AggregateError`, with `results`: rows changed per statement, null where one failed) for batches, and `isRetryable()`. `message` and `code` keep their values. A server error without text is named after its code instead of having `message === undefined`.

- New: `getConnectedHost()` (never connects), `getQueueLength()`; `getDatabaseParameter()` / `setDatabaseParameter()` take a name (`'ISOLATION_LEVEL'`, `'isolationLevel'`) as well as a number.
- Fix: a method given a callback now also settles its promise. `await conn.query(sql, cb)` used to hang for ever. With a callback, the promise is marked handled, so a failure does not also become an unhandled rejection. Callbacks are called once; one that throws no longer has its own exception reported back to it as a second call.
- Fix: `queryAsObjects()` with a callback could call it twice and resolved even when the query failed.
- Fix: `beginTransaction()` before the first request was undone by the login, which reset auto-commit to on — begin, delete, rollback, and the rows were gone. The auto-commit choice now survives the login and any reconnect.
- Fix: `executeWithTypedParams()` left the prepared statement's handle open on the server, one per call; it is closed now. A failed execute after a successful prepare closes its handle too.
- Fix: `_writeLong` wrote negative values wrongly (-1 went out as 4294967295) and threw on a BigInt.
- Fix: the old-protocol `query()` of a statement that returns no rows threw a TypeError; it resolves with `result: undefined` and a closable handle, like the new protocol.
- Change: `execute()` resolves with the rows changed (an array for an array); `batchExecuteNoQuery()` resolves with one count per statement; `executeWithTypedParams()` resolves with the rows changed. They resolved with nothing.

## Version 0.9.5 (Oct 07, 2026)

- New: `CoraDBConnection.getQueryPlan(sql)` returns the plan the engine would use for a statement. The plan is not a result set and never arrives as rows: it has a request of its own, `CAS_FC_GET_QUERY_INFO` with `QUERY_INFO_PLAN`, sent against query handle 0 together with the SQL. The statement is compiled but neither prepared nor executed, so this is safe to ask about a `DELETE` you have no intention of running. This matches `UConnection.getQueryplanOnly()` in the JDBC driver.
- New: `src/packets/GetQueryInfoPacket.js`.
- Fix: `cancel()` sent a request no CAS listener recognises, so it was refused in silence and every cancel fell through to `abort()` — which stops the statement by closing the connection and rolling the transaction back, the one outcome `cancel()` exists to avoid. Three things were wrong and all three are corrected: the ten bytes are now `'X'`, `'1'`, `CAS_VERSION`, three reserved zeroes and the process id (the word `CANCEL` was a guess, and not the protocol); the process named is the login response code rather than `sessionId`, which is a different number the listener has never heard of; and the request goes to the port the connection is served on (`connectionBrokerPort` after the client-info exchange) rather than the port in the connection string, which the broker may well have handed the client away from.
- Fix: a cancel is accepted on any non-negative answer. Only a negative integer is a refusal; insisting on exactly zero would have turned accepted cancels into aborts.
- Change: `OpenDatabasePacket` no longer publishes `casProcessId`. It was an alias for `sessionId`, which is not the process id a cancel names; 0.9.4 added it on that mistaken reading. `sessionId` is unchanged and still public.
- Test: `test/unit-test/test_CoraDBConnection.cancel.js` runs `cancel()` against a listener that answers the way a CAS does, and asserts the ten bytes that go out, the process id they name, that an accepted cancel leaves the connection and its transaction alone, and that a refusal falls back to an abort. A cancel that is silently wrong does not fail — it just does not stop anything — so nothing short of reading the bytes catches it.
- Note: raising the session's optimizer level (`SET OPTIMIZATION LEVEL 257` and friends) makes the engine *produce* a plan and print it to the server's own output. Nothing comes back down the connection, which is why that route leaves a client with nothing to show. The JDBC driver never sets it.

## Version 0.9.4 (Oct 05, 2026)

- New: `CoraDBConnection.cancel([options])` stops the statement a connection is executing. It first asks the broker out-of-band — a CAS process busy with a statement is not reading its own socket, so the request goes to the broker on a socket of its own and names the CAS by process id — and falls back to `abort()` if that is refused or unanswered. It resolves with `{ method: 'broker' | 'abort' }`, because the difference matters: a broker cancel leaves the connection, its session and its transaction intact, while an abort does not. `cancel({ brokerCancel: false })` goes straight to `abort()`, and `cancel({ timeout })` sets how long the broker is given (default 2000 ms).
- New: `CoraDBConnection.abort([reason])` takes the connection down and answers everything waiting on it: the request on the wire, and every request still queued behind it. Until now there was no supported way to stop a request — `close()` queues behind the statement it is meant to interrupt. The connection can be opened again afterwards.
- Fix: `Queue.empty(reason)` now reports a failure to each request it removes, and `push`/`unshift` take the handler that does it. Dropping a queued request used to discard it without settling the promise its caller was waiting on, so that caller waited for ever. `close()` passes a reason too, which is where the leak actually bit.
- Change: `Queue` takes an item off the list at the moment it starts rather than when it is scheduled. In between the two it belonged to nobody — still waiting, but no longer something `empty()` could find and answer.
- Change: `getQueryPlan()` is enqueued first and connects inside the queue slot, the way every other request works, so it is visible to `empty()` from the start.
- New: `CoraDBConnection.canBrokerCancel()` and `getCasProcessId()` report whether an out-of-band cancel is possible on this connection and which CAS process it would name.
- New: `src/packets/CancelRequestPacket.js` — the broker's ten-byte cancel (`CANCEL` plus the CAS process id, big-endian) and its four-byte reply.
- New: `tools/check-cancel.js` confirms against a live broker that the out-of-band cancel is accepted, what the cancelled statement returns, and whether the connection survives it. The packet-level behaviour is covered by unit tests; whether a given broker honours the request is not something a unit test can answer.
- Change: `OpenDatabasePacket` publishes the integer after the broker information as `casProcessId` as well as `sessionId`. The field has always been read; in the CAS protocol it identifies the process serving the connection, which is what a cancel has to name. `sessionId` is unchanged.
- New: `ErrorMessages.ERROR_ABORTED`, `ERROR_CANCEL_TIMEOUT` and `ERROR_CANCEL_REFUSED`.
